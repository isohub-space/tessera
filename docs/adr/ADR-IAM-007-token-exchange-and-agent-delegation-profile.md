## Background

An agent is software that does work for a person: it reads their files, calls an API, or asks another agent to do part of the job. Today tessera can give an agent a token in two ways. With `client_credentials` the agent acts for itself. With the authorization-code flow it acts for a signed-in person, but the token looks exactly like one the person's own app would hold. In neither case can the API that receives the token tell that an agent is acting, or for whom, and an agent that wants a helper to do part of the job can only hand over its own token.

The standard answer is the token exchange grant (RFC 8693). A client presents a token it holds and gets back a new one that names the person in `sub` and the agent that acts in an `act` claim. Each further hop adds an `act` layer, so the token shows the whole chain. RFC 8693 is a framework, not a policy: it does not say who may exchange what, how far a chain may grow, or whether the new token may be wider than the old one. Tessera has to supply those rules.

Tessera has so far refused token exchange. `GrantType` is a sealed interface whose permitted members are authorization code, client credentials and refresh token (`dom/client/grant/GrantType.java:19-20`). The sealing guards registration parsing (`pers/client/OAuthClientMapper.java:91-97`) and per-client grant checks, but `/token` dispatches on grant-type strings (`rest/TokenResource.java:63-66,119,173-175`), so a new branch there compiles without touching `GrantType`. D7 adds the guard that makes the compile-time claim true. The two design notes wrote the rules for exchange, and this record adopts them, so the exclusion can be lifted for this one grant and replaced by checks that enforce the rules.

**The maintainers' rule for every choice tessera offers:** a choice is configurable only if none of its states weakens security, and every configuration point declares its states and their consequences. Every state of every configuration point keeps the five-property security floor of the second design note: a key-authenticated actor, sender-constrained tokens, single use of hand-offs, client assertions and forwarded proofs across instances and realms, realm isolation, and a revocable chain. A state below the floor is not offered, however useful it would be for interoperability. Every decision below refers to this rule.

Path abbreviations as in the second design note: `api/` = `tessera-api/src/main/java/dev/tessera/iam/application/`, `dom/` = `tessera-domain/src/main/java/dev/tessera/iam/domain/`, `rest/` = `tessera-rest/src/main/java/dev/tessera/iam/adapter/rest/`, `pers/` = `tessera-persistence/src/main/java/dev/tessera/iam/adapter/persistence/`, `mig/` = `tessera-persistence/src/main/resources/db/migration/`, `props` = `tessera-server/src/main/resources/application.properties`. Code references are at `main` commit `fdabe13`; the second design note cites the same code at `09189b2`, before an unrelated change shifted some line numbers.

Facts the decisions rest on:
- A confidential client is registered with one of four methods (`ClientAuthMethod`): mTLS, `private_key_jwt`, a keyless workload-identity assertion (an RFC 7523 JWT that a trusted external issuer signs), or a client secret. Only the two assertion methods authenticate by key today. A client registered as mTLS still authenticates with its secret. The client certificate comes from the `X-Client-Certificate` header with no trust switch, and is read even in fixed-tenant mode, which `props:159-166` defines as having no header-asserting gateway (`rest/token/ClientCertificateThumbprint.java:33`; `rest/TokenResource.java:92,129,169`). It is only checked for presence and becomes the token's `cnf` whatever the method, so the header-derived `x5t#S256` is as untrusted as possession proof as it is as authentication. RFC 8705 §2 client authentication is not built.
- A client assertion is accepted only on `client_credentials`. The authorization-code grant at `/token` takes a secret or no client authentication, and `/revoke` and `/introspect` do not authenticate assertion clients at all. A `private_key_jwt` assertion's spent `jti` is keyed per realm while its `aud` is the one global issuer, so one assertion is accepted once per realm that registers the same id and key (`rest/token/AssertionReplayStore.java:61`; `rest/token/NimbusClientAssertionVerifier.java:131,194-195,240-241`). The verifier does not check the JWS `typ` (`:159-163`). A workload-identity token is reusable until `exp` unless its issuer enforces single use (`:186-196`). The replay stores are per instance.
- DPoP proofs are accepted only from public clients on the authorization-code grant (`api/TokenService.java:271-287`). The validator has no `ath` check and no nonce, compares `htu` by exact equality with one configured URL, and keys its replay map by `jti` alone, uncapped, pruned by a full scan per proof, per instance (`rest/token/NimbusDpopProofValidator.java:50,76-131,148-150`). `proofMaxAge` and `clockSkew` have no upper bound (`rest/config/DpopConfig.java:24-33`).
- With `iam.authflow.require-sender-constraint=false` a confidential non-mTLS client receives an unbound Bearer token (`api/TokenService.java:288-297`; `api/ClientCredentialsService.java:154-161`; default `true` at `props:192`). Access-token lifetimes have no upper bound (`api/TokenService.java:132,406-411`; `api/ClientCredentialsService.java:103-107`).
- A refresh-token family keeps one predecessor hash for replay detection (`dom/refresh/RefreshTokenFamily.java:49-62`); access tokens carry no family link. A refresh re-mints the access token without `cnf` and without scope (`api/RefreshService.java:275-292`).
- Authorization-code and refresh access tokens are RFC 9068 JWTs whose `aud` is the issuer. `client_credentials` already takes `resource`, and its tokens name the client's registered audiences, possibly several. `/authorize` takes no `resource` (`rest/AuthorizeResource.java:99-109`), and emits `iss` on its responses (`:196,199`) without advertising `authorization_response_iss_parameter_supported`. Nothing handles `dpop_jkt` or `dpop_bound_access_tokens`.
- Only `client_credentials` access tokens carry the realm claims (`realm_tenant`, `realm_baseline`). Keysets are per tenant and the issuer is one configured string on every mint path, so a signature does not tell two baselines of one tenant apart (ADR-IAM-003 D4b). A client identifier is unique only per `(tenant, baseline)` (`mig/V3__iam_core_entities.sql:55`).
- Introspection reports `token_type` `Bearer` and no `cnf` for every access token, treats a token without `exp` as active, and is open to any public client by `client_id` (`api/IntrospectService.java:72,113,116-117`; `api/ClientAuthentication.java:44-50`). `/revoke` acts only on owned refresh families (`api/RevokeService.java:77-99`).
- Consent is stored but never checked: `ConsentService.hasConsented` (`api/ConsentService.java:29-31`) has no caller in main code, and the authorization-code grant records whatever scopes the request names (`api/AuthorizationService.java:75`; `api/ClientRequestCheck.java:31-45`).
- No registration API exists. The only production creator makes `CLIENT_SECRET` clients (`pers/bootstrap/FirstBootProvisioner.java:150-170`), and the domain constructors do not relate method and grants (`dom/client/ConfidentialClient.java:73-107`, `dom/client/PublicClient.java:40-61`).
- No scheduled job removes expired rows from any table.
- Threat model rows 18 to 25 were written before the capability; each names the test that must exist before the row is pinned.

## Configuration points

**The rule.** Configuration points follow one rule, stated once here and referred to by D1, D2 and D5:
1. **Ordered states.** Each point's states are totally ordered from the default upwards. No state is below the floor.
2. **Deployment value and client value.** The operator sets a deployment minimum. A client registrant may set a stricter value for its own client. The effective value is the stricter of the two.
3. **Only the operator lowers.** A stored per-client value can be lowered only by the operator, as an audited security event. Lowering the deployment minimum does not lower clients whose stored value was set under the higher minimum. A client without a stored value follows the deployment minimum down as well as up, and lowering the minimum is itself an audited event.
4. **Chain monotonicity.** A hop's effective level is at least the effective level of the token it derives from. A delegation grant (set by the person or the operator) may carry a minimum. An exchange or redemption is refused with `invalid_client` when the actor cannot meet the highest of the deployment minimum, its own value, the parent hop's level and the grant minimum.
5. **The level travels in the token.** The effective level of each hop is stamped into its `act` object, so a resource server, which cannot read another client's registration, can require a minimum per tool, as it would use `acr` for a person.
6. **Fail at startup.** An unknown state name, or a value outside the declared bounds, fails startup; nothing is clamped silently. A state marked "later" is an unknown name until the change that implements it ships. A stored per-client value outside the declared states is refused when it is written and treated as `invalid_client` when it is used.
7. **Capability caps read the other way.** Where the stricter state is "off" (the intermediary), the point is an operator allow-list per registered client, not a minimum a client raises.

**`exchange.actor-proof`** (D1). Ordered `client-key` < `client-attested-key` < `attested-instance`.

**Existing configuration points that must be bounded before the exchange grant can be enabled.** The rule applies to every configuration point, not only the new ones:
- Access-token lifetimes have no upper bound (`api/TokenService.java:132,406-411`; `api/ClientCredentialsService.java:103-107`).
- `iam.authflow.require-sender-constraint=false` issues unbound Bearer tokens (`props:192`); restricted by D5.
- `iam.subject.trust-header=true` trusts `X-Subject-Id` verbatim (`props:208-216`).
- Multi-tenant mode trusts `X-Tenant-Id` verbatim (`rest/tenancy/TenantResolutionFilter.java:84-88`); the per-realm issuer track is the answer.
- Workload issuers may be configured with single use and `jti` off (`rest/token/NimbusClientAssertionVerifier.java:186-196`); excluded from the exchange by D1.
- DPoP `proofMaxAge` and `clockSkew` have no upper bound (`rest/config/DpopConfig.java:24-33`).
- `X-Client-Certificate` has no trust switch at all (`rest/token/ClientCertificateThumbprint.java:33`).

## D1 — The actor is the key-authenticated client; tessera issues no separate actor token

**Decision.** The actor of an exchange is the client that authenticates the request at `/token`, and it must authenticate with a key: `private_key_jwt`, or a workload credential that carries a key (`cnf`) or comes from an issuer that enforces single use with a `jti`. mTLS qualifies only once RFC 8705 §2 authentication is real client authentication over TLS that tessera terminates or an authenticated edge hop. A client secret is not accepted for this grant, and a public client cannot use it. Tessera never issues a separate actor token to an intermediary (the maintainers' decision, 2026-10-29). What a client may send as `actor_token` is the configuration point `exchange.actor-proof` (above): in its default state `client-key`, only the client's own assertion, with both `jti`s spent atomically, and any other `actor_token` is refused with `invalid_request`. In every state the assertion verifier refuses a JWT whose `typ` is `dpop+jwt`, the hand-off `typ` or the redeemer-key-statement `typ`; the redeemer key statement carries its own explicit `typ`, and its verifier accepts no other. A client assertion is single use across instances and realms: the `private_key_jwt` spent set is global, keyed by the registered key's thumbprint and the `jti`, and the `jti` is spent on every authenticated attempt, refused ones included. Authenticating as a client is never by itself a right to act for someone: that right comes from a delegation basis (D4).

**Errors.** `invalid_client` when authentication fails or the chain level cannot be met; `invalid_dpop_proof` when the proof's key does not match; `invalid_request` for a malformed or foreign `actor_token`. The assertion `jti` is already spent when `invalid_dpop_proof` is returned, so the distinct error tells an interceptor nothing it can reuse.

**Consequences.**
1. One credential per actor. A client cannot present a credential it was lent, which is the copied-credential case this profile exists to rule out (threat model row 24).
2. An MCP gateway acting as a resource server, or any other intermediary, is a confidential client that authenticates by key like any other actor. Whether and how it may exchange a token it received is the intermediary rule of D2.
3. The hand-off token of D2 is not an actor token. It is a one-time grant artefact that one named client may redeem once, and its redeemer is still identified by its own authentication.

**Why.** An actor token issued to the intermediary is a second credential to steal and lets the actor's identity travel separately from the key that proves it. Accepting the client's own assertion as `actor_token` is not issuing one, and it keeps conformance with actor-profile §6.4.1. DPoP is bound to client authentication only by sharing the TLS tunnel (RFC 9449 §11.11), so a copied assertion can be paired with a DPoP key the client never held; `client-attested-key` closes that gap by naming the DPoP key in the assertion. Using the long-term client key as the DPoP key was dropped: it moves the long-term key into every resource-server request, turns a DPoP key leak into identity compromise, removes instance and task separation, and makes rotation strand live tokens.

## D2 — How a chain is built

**Decision.** Every token tessera mints for an agent acting for someone carries the person (or, for an autonomous chain, the root client) in `sub` and the acting chain in nested `act` objects. An autonomous chain starts from an autonomous root (the maintainers' decision, 2026-10-30): a `client_credentials` token minted for a registered agent client under an operator-configured grant (D4) and recorded in lineage (D6). The root carries no `act`; every token derived from it does. Each `act` object names its actor by `iss` and `sub`, where `act.iss` is, from the first delegated token, the realm's issuer URL that ADR-IAM-003 D3 will make the token issuer, `base/realms/<opaque id>`, with one opaque id per `(tenant, baseline)`. Actors are compared by the pair `(act.iss, act.sub)` everywhere: cycle check, `may_act` reconciliation, chain monotonicity and resource-server allow-lists. A chain whose actors span realms is refused. Each `act` object also carries the hop's effective levels (`exchange.actor-proof`, `handoff.redeemer-binding`). The token's own `iss` stays global until the per-realm issuer ships on its own track; actor identifiers, stored grants and allow-lists do not change when it does. Tessera builds `act` itself and never copies an inbound one. The outermost `act` is the current presenter and equals `client_id`; inner `act` objects are a record, not an input to access decisions (RFC 8693 §4.1). The exchange grant has no impersonation output: no request produces a token without `act`.

The chain grows in three ways, as the design notes describe. The first hop is the authorization-code flow for a client registered as an agent, whose token already carries `act`. An actor exchanges its own token for another resource inside its grant. And an actor hands a narrower right to a named sub-agent in two steps, through a hand-off token. The hand-off is a JWT assertion grant in the actor-profile §4.1 shape, typed `urn:ietf:params:oauth:token-type:jwt` with its own explicit `typ`: `aud` is the issuer of the realm it is minted in: today the one configured issuer, `iam.oidc.issuer`, which is the only audience the assertion verifier accepts; once the per-realm issuer ships (ADR-IAM-003 D3), `base/realms/<opaque id>` for that `(tenant, baseline)` in multi-tenant mode and `base` in single-tenant mode, never another realm's issuer (not the token endpoint, matching tessera's issuer-only assertion audience, `rest/token/NimbusClientAssertionVerifier.java:76-81`); `sub` is the person; `act` is the parent's chain; `may_act` names the sub-agent by `(iss, sub)`; it carries the permitted resource set; its `jti` is single use, consumed in the lineage store across nodes; it lives at most 60 seconds.

Who may present a subject token:
- **Same-actor exchange.** The authenticated client equals the subject token's outermost `act.sub` (for an autonomous root, which carries no `act`, its `client_id`), and the request carries the proof for the subject token's `cnf`. The output is bound to the key of the proof that matched the subject token's `cnf`, never to a second proof in the request.
- **Hand-off redemption.** The hand-off token's `may_act` names the authenticated client, under `handoff.redeemer-binding` (D5).
- **An intermediary exchanging a token it received** (an MCP server or gateway acting as a resource server, whose subject token's `aud` is itself): the configuration point `exchange.intermediary`, an operator allow-list per registered gateway, default `off`, which is the stricter state. In `rebind-live-proof` the presenter rebind is accepted only when all of these hold:
  1. The gateway authenticates by key (`exchange.actor-proof` applies).
  2. The subject token's single `aud` equals the gateway's operator-set registered resource identifier.
  3. The requested resource is in the downstream set the gateway declared at registration and the grant names (shown at consent).
  4. The caller's DPoP proof is forwarded as the profile parameter `subject_token_proof`, with `ath` equal to the hash of the exact subject token, a key whose thumbprint equals the subject token's `cnf.jkt`, `htu` equal to the registered resource or having it as prefix on a path-segment boundary after RFC 9449 normalisation, and an age of at most 60 seconds from `iat` under a ceiling fixed at startup.
  5. The proof's `jti` is spent in a shared, capped store keyed by `(realm, jkt, htu, jti)`, separate from token-endpoint proofs, atomically with the lineage record and also on refusal; at most one exchange per `(proof jti, resource)`.
  6. The subject token is active in lineage, and an mTLS-bound subject token is refused.

  The output is bound to the gateway's key, depth plus one, with no refresh token, rate-limited per gateway.

**Who may start a hand-off (fixed rule).** Only a key-authenticated actor may start a hand-off. DPoP is "not a client authentication method" (RFC 9449 §1): a public agent's key proves session continuity, not which registered client it is. A public agent reaches delegation in one of two ways. Later, attestation-based client authentication makes it a key-authenticated client. Today, the person delegates to the sub-agent directly: the sub-agent runs its own authorization-code flow, and the result is a child grant inside the parent's grant, naming the parent, with resources and scopes that are subsets of the parent's, counted in the parent's depth, and cascading when the parent's grant is withdrawn. The consent screen names the requesting parent and the limit.

**Declared residual of `rebind-live-proof`.** While compromised, a gateway can obtain one downstream token per declared resource, at the subject token's full scope, for each user connected to it, renewed with each new inbound token, and it can solicit requests from connected clients to get fresh proofs. MCP uses one endpoint URL for every tool, so `htu` carries no per-tool intent. Tokens of callers no longer sending requests are safe. This equals what an honest gateway is allowed to do, which is inherent in naming it in the grant.

**Consequences.**
1. A subject token is accepted only if tessera issued it, it is active, it is an access token (`typ=at+jwt`) or a hand-off token, and it belongs to the realm of the request, compared on the token's realm claims against `(tenant, baseline)`; a token without them is refused. It must also be recorded in lineage (a hop-1 agent token, an autonomous root, an exchanged token or a hand-off token): a token without `act` that is not recorded is never a subject token. ADR-IAM-003 D4b stamping of the realm claims on every mint path, and the realm-registry slice that mints one opaque id per `(tenant, baseline)`, are prerequisites. A token from another issuer is refused; cross-domain chains wait for identity chaining.
2. A sub-agent never receives its parent's token.
3. A resource server authorizes the pair of `sub` and the outermost `act.sub` within the token's realm, never `sub` alone when `act` is present (first design note, D5).
4. No path issues a Bearer refresh: in any agent, `act` or subject-token path, refresh re-emits `act`, a persisted and continuity-checked `cnf`, the scope and the realm claims, or no refresh token is issued. An unbound subject token is refused with `invalid_grant`.
5. A sub-agent whose parent is a public agent is reached through a child grant, never through an unlinked grant of its own.

## D3 — Attenuation at every hop

**Decision.** Tessera enforces, at every exchange, the rules below. A request that breaks one is refused; the client learns which rule from the error code only, never the content of the subject token.

| Rule | Check | Error |
|---|---|---|
| Scope only narrows | requested scope ⊆ the subject token's scope, by exact string; no scope hierarchy is expanded | `invalid_scope` |
| Audience only narrows | requested resource ∈ the subject token's permitted resource set (recorded in lineage) ∩ the grant's resources ∩ the actor's registered audiences | `invalid_target` |
| One audience | each delegated token names exactly one resource: tessera's rule, not RFC 8707's | `invalid_target` |
| Fine-grained rights only narrow | `authorization_details` (RFC 9396) accepted only when every entry equals or is an exact subset of one in the subject token | `invalid_authorization_details` |
| Expiry never extends | `exp` ≤ the subject token's `exp` and ≤ the grant's expiry; at most 5 minutes from depth 2 on | issued shorter, never longer |
| Depth is capped | the new depth (the number of `act` layers) ≤ the lower of the deployment ceiling and the grant's limit; the ceiling is configurable up to **4**, default **2** (agent, sub-agent) | `invalid_request` |
| No cycles | on a hand-off, the new actor's `(iss, sub)` is neither the subject nor any `act` pair in the chain | `invalid_request` |
| Fan-out is capped | live children per parent `jti` and per grant stay under their caps | `invalid_request` |
| Rate | exchanges are rate-limited per (grant, actor) and per gateway | `invalid_request` |
| Chain level | the actor meets the highest of the deployment minimum, its own value, the parent hop's level and the grant minimum | `invalid_client` |
| No refresh token | an exchange never returns a refresh token; the actor exchanges again from its upstream token | — |
| Delegation basis | a grant naming the actor, or a hand-off token whose `may_act` names it (D4) | `access_denied` |

**Consequences.**
1. A deployment ceiling above 4 is a configuration error that fails startup, not a value that is clamped silently.
2. Because an exchanged token never comes with a refresh token, a chain cannot outlive its root's refresh family and grant, or for an autonomous root its `exp` and its operator grant: when the root's refresh family is revoked or the grant expires, every hop below has to stop. This holds only because each lineage row records the refresh family id of its root (D6); access tokens carry no family link today.
3. The target of an exchange is named by `resource`. The RFC 8693 `audience` parameter is accepted only on a hand-off, where it names the next actor.

## D4 — The delegation basis is a grant the person gave

**Decision.** A delegated token is issued only on a delegation basis: a standing delegation grant, or a per-task approval. The standing grant extends ADR-IAM-004's `(user, client)` consent with the resources, the scopes, the sub-agents the agent may hand off to (an explicit list; "any agent" is not offered), the maximum depth, an expiry (default 30 days, never open-ended), the downstream resources of any intermediary it names (shown at consent), and an optional minimum level per configuration point. A child grant (D2) references its parent grant, stays inside it and cascades with it. Changing any dimension asks again. Scopes that a resource server or operator marks as per-task are never covered by a standing grant and are approved per task with `authorization_details`. An agent acting for itself may hand off only under a grant an operator configured with the same dimensions; an autonomous root (D2) is minted only under such a grant.

**Consequences.**
1. The consent schema grows by those dimensions; this is the agent-registration and delegation-grant work of the design notes.
2. Withdrawing a grant refuses new exchanges for that `(subject, actor)` pair at once, and deactivates its child grants and every recorded token under them (D6).
3. Consent enforcement and a per-client scope allow-list on the authorization-code grant are prerequisites: the basis this decision extends is not checked today.

## D5 — Every delegated token is bound; no bearer state exists for delegation

**Decision.** Every access token issued to a client registered as an agent, every token carrying `act`, and every subject token of an exchange is sender-constrained (RFC 9700 §2.2.1): it carries `cnf`, the DPoP key thumbprint (`cnf.jkt`, RFC 9449) or, once the certificate trust switch is on, the client certificate thumbprint (`cnf["x5t#S256"]`, RFC 8705) of the hop that presents it. A header-derived `x5t#S256` is not possession proof until that switch is on. The exchange request itself must carry the matching proof for the subject token. Concretely:
- `require-sender-constraint=false` is not available to clients registered as agents, to any token carrying `act`, or to any subject token; startup refuses `false` while the exchange grant is enabled.
- A refreshed token in these paths is never Bearer: refresh keeps the `cnf` persisted with its family and checked for continuity, the scope and the realm, or no refresh token is issued (D2).
- Tessera mints a token carrying `act` for a resource only if that resource is registered as verifying sender constraint (the counterpart of RFC 9728's `dpop_bound_access_tokens_required`).

The bound paths are widened so that the cost falls without weakening anything: `dpop_jkt` at `/authorize` (RFC 9449 §10), declared with its caveat that the protection holds only with a unique DPoP key per authorization request; the `dpop_bound_access_tokens` client metadata (RFC 9449 §5.2) honoured at registration; `private_key_jwt` on the authorization-code grant, so a server-hosted MCP client can be confidential; `resource` at `/authorize`, the RFC 9207 `authorization_response_iss_parameter_supported` flag, and `revocation_endpoint` and `introspection_endpoint` metadata; a DPoP verifier with conformance vectors in the resource-server guide; and a documented local bridge pattern, in which a stock stdio MCP client talks to a local bridge that performs OAuth and DPoP and keeps the key.

**The hand-off token** has its own `typ` (not `at+jwt`), introspects as inactive and is refused by every resource server (RFC 9068 §4). It is a one-time grant artefact bound to a key-authenticated client, as RFC 6749 binds a confidential client's code to its authentication; how tightly it is bound to the redeemer's key is the configuration point `handoff.redeemer-binding` (above), chosen by the redeemer's registrant: `client` by default, `client-and-key` with a signed redeemer key statement whose key is checked for equality and never copied, and `attested-instance-key` later. Tessera never applies the actor-profile draft's §13.3 rebind over a bound hand-off. The per-task protection of `client-and-key` holds only if the sub-agent uses a distinct DPoP key per task, which is declared.

**Consequences.**
1. A token stolen from one hop is useless to another hop or a thief (threat model row 23).
2. DPoP for confidential clients, `dpop_jkt` and `dpop_bound_access_tokens` are prerequisites.
3. A resource server checks proof of possession against the top-level `cnf` only, refuses a token that has `act` but no `cnf`, and refuses a token with `cnf` presented as `Bearer`; the resource-server guide requires both. Introspection reports `cnf` and the true `token_type`.
4. **Declared consequence for MCP.** MCP hosts that enable the TypeScript SDK's client DPoP support (2.1.0 and later, opt-in) connect; other stock MCP clients connect only through the bridge pattern or as confidential clients. Revisit when MCP's DPoP profile (SEP 1932, with ext-auth pull request 33) is merged or the Python SDK ships client DPoP. When Client ID Metadata Documents are added later, a client's `jwks_uri` and web domain become a trust anchor for actor identity, and threat row 17 (SSRF) reopens; both are declared with that change.

## D6 — Revocation through lineage

**Decision.** The lineage store records every token tessera mints that carries `act`, hop-1 agent tokens included, every autonomous root (D2), and every hand-off token: its `jti`, its parent's `jti`, its root's `jti`, its delegation grant, its root's refresh family id, its actor, its permitted resource set, its effective levels, its expiry, and when it was revoked or consumed. The active check of an exchange and of introspection fails closed for recorded tokens: a miss or a store error is inactive. Unrecorded tokens without `act` keep signature, `exp` and realm checks (ADR-IAM-003 D4) and are never subject tokens; recording every access token is a later, separate decision.

Who may revoke: a delegated token and its subtree may be revoked by the subject, the root client, any ancestor actor in its chain, and its own holder; nobody else. Withdrawing a grant deactivates every token issued under it, including child grants. Disabling a client deactivates every recorded token whose chain contains it and refuses its exchanges. These are documented as tessera extensions of RFC 7009, whose §2.1 lets only the client a token was issued to revoke it. Cascade is by grant id and by a per-root epoch, each one indexed update, with caps on live children per parent `jti` and per grant and per-tenant quotas, so the store cannot be made a denial-of-service lever. A scheduled cleanup removes expired rows. `/revoke` and `/introspect` accept client-assertion authentication, since D1's actors authenticate only that way. Revoking a link does not stop re-issuance from an upstream refresh family: only withdrawing the grant, revoking the family or disabling the client does.

**Rollout (the maintainers' decision, 2026-10-29).** The single-hop token exchange grant stays disabled until the lineage store, store-backed introspection and client-assertion authentication at `/revoke` and `/introspect` have shipped, and until the existing configuration points above are bounded: lifetime caps, DPoP age and skew caps, the certificate trust switch, and the closure of `require-sender-constraint=false`. These are hard prerequisites, not follow-ups: there is no window in which tessera has issued a delegated token that cannot be revoked.

**Consequences.**
1. A resource server that validates the JWT locally sees a revocation only at expiry: at most 5 minutes from depth 2, and at most the hop-1 lifetime cap, whose value is declared with the cap. That is why delegated tokens are short-lived (D3) and why an operation whose effect cannot be undone introspects the token instead.
2. Introspection reports `act`, `aud`, `iss` and `cnf` (option 2 of the threat model's open `iss`/`aud` decision, taken for delegated tokens), and introspection of recorded tokens is limited to authenticated confidential clients.
3. Fail-closed means a lineage-store outage stops delegation and the introspection of recorded tokens.
4. The second design note's "Declared residuals" also apply to this record, among them four that no rule here closes: a confused deputy steered by prompt injection, a cross-user mix-up inside a multi-user agent, co-located factors on one host, and gateway-side replay of forwarded proofs.

## D7 — The compile-time exclusion is lifted for token exchange only, and the profile's checks replace it

**Decision.** `GrantType` gains a `TokenExchange` member (`urn:ietf:params:oauth:grant-type:token-exchange`) in the change that implements the single-hop grant, not before. Implicit, ROPC and device code stay excluded at compile time. What the exclusion is meant to guarantee (no code path can mint a token through exchange) is replaced by these guards, each pinned by a test:

0. **Dispatch through the type.** `/token` dispatches through a `GrantType` parse with an exhaustive switch, or an architecture rule forbids grant-type literals outside the domain. Without it the compile-time claim is false today.
1. **Registration.** Only a confidential client whose authentication method is `private_key_jwt` or workload identity may be registered with the token exchange grant (mTLS once RFC 8705 §2 authentication is built, D1). A public client or a client-secret client is refused by a new domain invariant on `ConfidentialClient` plus a database `CHECK`, and a registration surface has to be built, since none exists. A client registered for the exchange must meet `exchange.actor-proof` at its effective level, and a workload client qualifies only with `cnf` or with enforced single use and `jti`.
2. **Off by default.** The grant is disabled by deployment configuration until enabled, and then only for the clients registered with it. It cannot be enabled before D6's prerequisites have shipped (D6, Rollout).
3. **No impersonation by type.** The domain type for an exchanged token cannot be constructed without a non-empty actor chain and a `cnf`, so the "token without `act`" and "unbound delegated token" outputs do not exist. The exchange handler reaches the signer only through that type, which a new architecture test pins (no rule constrains `TokenSignerPort` callers today), and a response-level test checks that every exchanged token has `act` and `cnf`.
4. **One policy.** The D1 and D3 checks live in one domain policy that the exchange handler cannot bypass, and each rule has a refusal test.
5. **Threat rows before release.** Rows 18 to 21 and 24, and the binding half of row 23 (`unboundDelegatedTokenIsNeverIssued`), move from deferred to pinned in the same change that adds the member. Row 22 and the hand-off half of row 23 (`handoffTokenIsRedeemableOnceByTheNamedActorOnly`) follow with the hand-off change. Row 25 is pinned by the lineage change, which ships before the grant can be enabled (D6, Rollout). The new rules add these refusal tests: a live proof for another token under the same key; an `htu` on a sibling path; a forwarded proof replayed across nodes; a hand-off redeemed with a proof for a key other than the statement's `jkt`; a redeemer key statement naming another client, refused at minting; a chain level below the parent's; a stored level lowered by a non-operator; startup with an unknown state or an out-of-bounds value. `GrantTypeTest` keeps its exhaustive switch with no `default`, now over four members, and the package documentation and `GrantType` Javadoc name only the three excluded grants.

**Prerequisites.** Before the grant can be enabled, these must have shipped (D6, Rollout): the lineage store, lineage-backed revocation and introspection, client-assertion authentication at `/revoke` and `/introspect`, and the bounded existing configuration points. The facts above also leave these to build before or with the grant: consent enforcement and per-client scope allow-lists on the authorization-code grant; the realm claims on every mint path (ADR-IAM-003 D4b); the realm-registry slice that mints one opaque id per `(tenant, baseline)`; the global `private_key_jwt` spent set; shared, capped replay stores for assertions, DPoP proofs and forwarded proofs; `private_key_jwt` and DPoP for confidential clients on the authorization-code grant; `resource` at `/authorize`; `dpop_jkt` and `dpop_bound_access_tokens`; the resource registration attributes (resource identifier, "verifies sender constraint", declared downstream set); a refresh path that keeps `act`, `cnf`, scope and realm (D2); and RFC 8705 §2 authentication before mTLS qualifies (D1). The second design note orders this work.

**Why.** The exclusion was meant to guarantee that a dangerous flow could not appear by accident. Lifting it on purpose, together with type-level and tested guards and a dispatch that actually goes through the type, gives that guarantee for the flow tessera now wants: an exchange can only ever produce an attenuated, bound, delegated, revocable token.

## Rejected alternatives

- **Keep token exchange excluded.** Agents keep passing their own tokens to helpers, and resource servers keep seeing agents as the person.
- **Impersonation tokens (no `act`).** The resource server cannot tell an agent acted.
- **An actor token issued to an intermediary.** A second credential to steal, and a client could present one that is not its own (D1). This differs from accepting the client's own assertion as `actor_token`, which `client-key` allows.
- **Accepting a client secret for the exchange.** A shared secret is the weakest method: whoever copied it can present it, which is the borrowed-credential case D1 rules out.
- **Passing the parent's token to the sub-agent.** The copied credential, which the sub-agent cannot prove possession of anyway.
- **Transaction tokens for agent chains.** Bearer tokens for a whole trust domain, not replay resistant; for propagation inside one call graph only.
- **Re-signing every hop with the chain in an HTTP field.** Not an OAuth token format, no revocation, and a second verifier for every resource server.
- **Deriving delegation from `client_id` or `azp`.** A token issued to a client says nothing about whose authority it uses.
- **Plain rebind for intermediaries (no caller proof).** It accepts the input's sender constraint on the gateway's word, and a compromised gateway could launder every harvested unexpired token; its residual is strictly larger than `rebind-live-proof`'s.
- **Bearer tokens at hop 1, in any form** (short-lived, single-audience, non-exchangeable, or with session, IP or user-agent checks). Below the floor (RFC 9700 §2.2.1): a stolen token is usable by anyone, and it is the subject token an intermediary would exchange.
- **Refusing every `actor_token`.** No stronger than `client-key`, and it breaks actor-profile conformance and clients that send their own assertion as `actor_token`.
- **DPoP key equal to the long-term client key.** Moves the long-term key into every resource-server request and turns a DPoP key leak into identity compromise (D1, Why).
- **A bearer access token as `actor_token`.** A second, stealable credential.
- **An `actor_token` naming a principal other than the authenticated client.** The actor would not be key-authenticated.
- **A keyless, reusable workload token as actor credential.** It proves possession of nothing.
- **A bare parent-supplied `jkt` for the redeemer key.** A parent could substitute its own key; the signed redeemer key statement replaces it.
- **A public (DPoP-only) agent starting a hand-off.** DPoP is not client authentication.
- **The person delegating to a sub-agent through an unlinked grant.** No cascade, no attenuation, and a consent-phishing channel; replaced by the child grant.
- **Hand-off audience = the token endpoint.** Conflicts with tessera's issuer-only assertion audience, adopted after the 2025 audience-injection disclosure.
- **Revocation by the issued-to client only (RFC 7009 literal).** A parent could not contain a rogue sub-agent.
- **`act.iss` = the global issuer.** Every actor identifier, grant and allow-list would change when the per-realm issuer ships.
- **One namespace per tenant with the baseline as a claim.** Signatures cannot separate baselines of one tenant.

## Open items

- **The hand-off token type**: decided, `urn:ietf:params:oauth:token-type:jwt` with its own explicit `typ` (D2). Its RFC 8693 §3 registry entry is quoted from actor-profile §6.6.1 and is to be confirmed in the hand-off change.
- **The `actor_unauthorized` error code**: decided. Tessera's token endpoint does not emit it; an exchange without a delegation basis is `access_denied` (D3). For resource servers, the validation guide says to answer `403` without that code until it is registered, and the code is adopted when it is.
- **`sub_profile` on `act` objects** (whether an actor is an agent, a person or a service): decided not in the first version; reopened if the actor-profile draft is adopted.
- **An intermediary exchanging a token it received**: decided, the configuration point `exchange.intermediary` (D2).
- **The consent page design**: assigned to the agent-registration and delegation-grant work. It builds on the hosted sign-in page of ADR-IAM-006 D2 and names the agent, every listed sub-agent, the downstream resources of any intermediary the grant names and, for a child grant, the requesting parent and the limit. The account page that lists and withdraws grants is assigned to the lineage and cascading-revocation work.
- **To confirm against the published texts in the implementing changes**: the RFC 9728 member name for a resource that verifies sender constraint, and the explicit assertion `typ` value from the RFC 7523 update.
- **Recording every access token in lineage**: a later decision (D6).
- **The `attested-instance` and `attested-instance-key` states**: after attestation-based client authentication is published.
