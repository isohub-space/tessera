## Verdicts

- **adopt**: stable enough to build on now; tessera should implement it or already does.
- **prototype**: worth building behind a flag or in a spike; the text may still move, or the value depends on another item landing first.
- **watch**: track it; do not build on it yet.

## Where tessera stands today

Read from the source on `main` on the survey date, so the ratings below start from fact rather than from the README:

- **Grants.** `authorization_code` with mandatory PKCE `S256`, `refresh_token` with family reuse detection, and `client_credentials` (enabled by configuration). `GrantType` is a sealed interface whose package documentation names token exchange, with implicit, ROPC and device code, as deliberately excluded "at compile time". Adding token exchange therefore reverses a recorded design choice and needs its own decision record, not only code.
- **Client authentication.** `client_secret` (Argon2id), `private_key_jwt` (RFC 7523), mutual TLS (RFC 8705), and a keyless `WORKLOAD_IDENTITY` method: a JWT client assertion issued by a configured trusted external issuer, such as a cloud platform's workload identity. The assertion path is wired for `client_credentials`.
- **Sender constraint.** Every access token on the authorization-code path is bound: DPoP (`cnf.jkt`, RFC 9449) for a public client, mTLS (`cnf["x5t#S256"]`, RFC 8705) for a confidential client. `client_credentials` binds with mTLS when a certificate is presented and can require it; it does not accept DPoP.
- **Audience.** `client_credentials` takes RFC 8707 `resource` and narrows to the client's registered audiences. `/authorize` does not accept `resource`, and the authorization-code path sets `aud` to the issuer (threat model row 14).
- **Discovery.** `/.well-known/openid-configuration` only; no RFC 8414 document, no `registration_endpoint`, no `authorization_response_iss_parameter_supported` although the authorization response carries `iss` (RFC 9207). Introspection does not echo `aud` or `iss`.
- **Registration.** No dynamic registration and no fetch of any client-supplied URL; threat model row 17 (SSRF) is deferred until one ships.

## Stable standards

| Item | Status (source, read 2026-10-28) | Verdict | What it means for tessera |
|---|---|---|---|
| OAuth 2.0 Token Exchange | RFC 8693, Proposed Standard, January 2020 ([rfc8693](https://www.rfc-editor.org/rfc/rfc8693.html)) | **adopt** | The only standard way to mint a token for an agent acting for someone else. Its `act` claim gives delegation semantics: "With delegation semantics, principal A still has its own identity separate from B" (§1.1). Nested `act` records prior actors, but "Prior actors identified by any nested act claims are informational only" (§4.1). It is a framework, not a policy: §5 sets no rule on which client may exchange which token, so tessera must supply the profile (who may act for whom, attenuation, depth). Reverses the compile-time exclusion noted above. |
| Dynamic Client Registration | RFC 7591, Proposed Standard, July 2015 ([rfc7591](https://www.rfc-editor.org/rfc/rfc7591.html)) | **prototype**, protected only | Open registration is an abuse surface for a public provider. The MCP specification of 2026-07-28 now marks it deprecated in favour of Client ID Metadata Documents (below). Worth having as *protected* registration (initial access token, software statement) for operators who provision agents in bulk. |
| DCR Management | RFC 7592, **Experimental**, July 2015 ([rfc7592](https://www.rfc-editor.org/rfc/rfc7592.html)) | **watch** | Experimental status, and the agent ecosystem is moving to URL-identified clients instead. |
| Rich Authorization Requests | RFC 9396, Proposed Standard, May 2023 ([rfc9396](https://www.rfc-editor.org/rfc/rfc9396.html)) | **prototype** | `authorization_details` expresses per-task, per-resource grants that scopes cannot. It is the natural carrier for per-task consent to an agent and for attenuation that is finer than scope strings. One vendor builds agent approval on CIBA plus RAR ([Auth0 asynchronous authorization](https://auth0.com/ai/docs/intro/asynchronous-authorization)). |
| DPoP | RFC 9449, Proposed Standard, September 2023 ([rfc9449](https://www.rfc-editor.org/rfc/rfc9449.html)) | **adopt** (shipped for public clients) | Extend to every delegated token, so each hop of a chain is bound to that hop's key. Accepting DPoP on `client_credentials` lets an agent without a client certificate still get a bound token. |
| mTLS client auth and certificate-bound tokens | RFC 8705, Proposed Standard, February 2020 ([rfc8705](https://www.rfc-editor.org/rfc/rfc8705.html)) | **adopt** (shipped) | Already the confidential-client binding. It is also the transport for X.509 SPIFFE identities (below). |
| Protected Resource Metadata | RFC 9728, Proposed Standard, April 2025 ([rfc9728](https://www.rfc-editor.org/rfc/rfc9728.html)) | **adopt** | A resource-server document, so tessera does not publish one for itself, but every MCP server must ([MCP authorization](https://modelcontextprotocol.io/specification/latest/basic/authorization)). Tessera's part is to issue tokens whose `aud` is the resource the metadata names, which needs `resource` at `/authorize`. |
| Resource Indicators | RFC 8707, Proposed Standard, February 2020 ([rfc8707](https://www.rfc-editor.org/rfc/rfc8707.html)) | **adopt** (half shipped) | MCP clients MUST send `resource` in authorization *and* token requests, and MCP servers MUST reject tokens not issued for them. Tessera accepts it only on `client_credentials`. |
| OAuth 2.1 | draft-ietf-oauth-v2-1-16, 3 September 2026, OAuth WG document, not yet an RFC ([datatracker](https://datatracker.ietf.org/doc/draft-ietf-oauth-v2-1/)) | **adopt** (as a target) | Tessera already meets its core: PKCE mandatory, no implicit or password grant, exact redirect matching, refresh rotation for public clients. MCP pins revision -13 as its base. |
| OAuth 2.0 Security BCP | RFC 9700, Best Current Practice, January 2025 ([rfc9700](https://www.rfc-editor.org/rfc/rfc9700.html)) | **adopt** (tracked in [rfc9700-checklist](../security/rfc9700-checklist.md)) | The baseline the identity-chaining draft points to for client authentication and sender constraint. |
| OpenID CIBA Core 1.0 | Final, 1 September 2021 ([openid.net](https://openid.net/specs/openid-client-initiated-backchannel-authentication-core-1_0.html)) | **watch** | The available standard for "ask the human on another device" before an agent acts. The WIMSE agent draft (below) cites it and says mid-execution user interaction still needs more specification work. |

## Drafts and emerging work

Working-group drafts first, then individual submissions. An individual draft has no IETF standing.

| Item | Status (source, read 2026-10-28) | Verdict | What it means for tessera |
|---|---|---|---|
| Transaction Tokens | draft-ietf-oauth-transaction-tokens-11, 30 July 2026, OAuth WG, state "WG Consensus: Waiting for Write-Up" ([datatracker](https://datatracker.ietf.org/doc/draft-ietf-oauth-transaction-tokens/)) | **watch** | Short-lived JWTs that carry the user and transaction context *inside one trust domain*, requested by RFC 8693 exchange with `requested_token_type=urn:ietf:params:oauth:token-type:txn_token`. Replacement may narrow scope but never widen it or change `txn`, `sub` or `aud`. The draft states they are not sender-constrained and not replay resistant. Relevant if tessera ever acts as a domain's transaction token service; not needed for agent-to-API delegation. |
| Identity and Authorization Chaining Across Domains | draft-ietf-oauth-identity-chaining-17, 19 July 2026, OAuth WG, intended Proposed Standard, **in the RFC Editor queue** ([datatracker](https://datatracker.ietf.org/doc/draft-ietf-oauth-identity-chaining/)) | **prototype** | Token exchange at domain A's server for a JWT authorization grant, then the RFC 7523 JWT bearer grant at domain B's server. It does not use `act`; actor information travels by "claims transcription", whose format it leaves open. The cross-domain step after token exchange, and close to final. |
| Identity Assertion JWT Authorization Grant (ID-JAG) | draft-ietf-oauth-identity-assertion-authz-grant-04, 21 May 2026, OAuth WG document ([datatracker](https://datatracker.ietf.org/doc/draft-ietf-oauth-identity-assertion-authz-grant/)) | **prototype** (after token exchange) | A profile of identity chaining in which the enterprise identity provider issues the grant. The MCP "Enterprise-Managed Authorization" extension, stable at 2026-07-28, is built on revision -04 and requires the resource's authorization server to advertise `urn:ietf:params:oauth:grant-profile:id-jag` ([ext-auth](https://github.com/modelcontextprotocol/ext-auth)). Okta ships it as Cross App Access ([Okta guide](https://developer.okta.com/docs/guides/ai-agent-token-exchange/-/main/)). |
| OAuth Client ID Metadata Document | draft-ietf-oauth-client-id-metadata-document-02, 6 July 2026, OAuth WG document ([datatracker](https://datatracker.ietf.org/doc/draft-ietf-oauth-client-id-metadata-document/)) | **prototype** | The client's `client_id` is an HTTPS URL to its metadata. | OAuth SPIFFE Client Authentication | draft-ietf-oauth-spiffe-client-auth-02, 15 June 2026, OAuth WG document ([datatracker](https://datatracker.ietf.org/doc/draft-ietf-oauth-spiffe-client-auth/)) | **prototype** | JWT-SVID as a client assertion (`urn:ietf:params:oauth:client-assertion-type:jwt-spiffe`), X.509-SVID over RFC 8705 mTLS, trust from a SPIFFE bundle endpoint per trust domain. Close to tessera's `WORKLOAD_IDENTITY` method; the gap is the assertion type and bundle-endpoint trust instead of a configured issuer JWKS. The draft still carries TODOs. |
| Attestation-Based Client Authentication | draft-ietf-oauth-attestation-based-client-auth-12, 13 October 2026, OAuth WG, "WG Consensus: Waiting for Write-Up" ([datatracker](https://datatracker.ietf.org/doc/draft-ietf-oauth-attestation-based-client-auth/)) | **watch** | Client instance attestation; the SPIFFE draft reuses it for WIT-SVIDs. Useful for agent attestation once a deployment has an attester. |
| Token Status List | draft-ietf-oauth-status-list-21, 21 June 2026, OAuth WG, in the RFC Editor queue ([datatracker](https://datatracker.ietf.org/doc/draft-ietf-oauth-status-list/)) | **watch** | Revocation status for self-contained tokens. A candidate for long-lived delegation grants; short-lived access tokens plus introspection cover the near term. |
| WIMSE architecture | draft-ietf-wimse-arch-08, 6 July 2026, WIMSE WG document ([datatracker](https://datatracker.ietf.org/doc/draft-ietf-wimse-arch/)) | **watch** | Workload identity across systems; the vocabulary the agent drafts build on. |
| WIMSE Workload Proof Token | draft-ietf-wimse-wpt-02, 27 August 2026, WIMSE WG document ([datatracker](https://datatracker.ietf.org/doc/draft-ietf-wimse-wpt/)) | **watch** | Application-layer proof of possession for workloads, an alternative to DPoP between services. |
| AI Identity Management System (AIMS) | draft-ietf-wimse-aims-00, 15 September 2026, WIMSE WG, Informational; **replaces** the individual draft-klrc-aiagent-auth ([datatracker](https://datatracker.ietf.org/doc/draft-ietf-wimse-aims/)) | **watch** (use as the map) | Maps existing standards onto agents rather than inventing new ones. Each agent MUST have a unique identifier (a SPIFFE ID may serve) and credentials bound to it; static API keys are "an antipattern"; the LLM MUST NOT hold agent or tool credentials; forwarding tokens downstream is an antipattern; token exchange and transaction tokens limit replay. Puts the agent in `client_id` and the user in `sub`, and does not mention `act`. Leaves policy format and mid-execution user interaction open. |
| OAuth Actor Profile for Delegation | draft-mcguinness-oauth-actor-profile-01, 9 October 2026, individual ([datatracker](https://datatracker.ietf.org/doc/draft-mcguinness-oauth-actor-profile/)) | **watch** (design input) | The most complete profile of RFC 8693 `act` for agents: issuer-scoped actor identifiers (`act.iss` + `act.sub`), the authorization server MUST NOT silently drop an inbound chain, implementations MUST enforce a local maximum depth, issued scope MUST NOT exceed the subject token's, proof of possession is checked against the top-level `cnf` only. ## Where tessera can differentiate

1. **Delegation, never impersonation, by construction.** Tessera already excludes insecure grants at the type level. A token exchange grant that can only *add* an actor to an `act` chain, and has no impersonation path at all, extends that guarantee. No surveyed open-source provider ships stable `act` delegation today.
2. **Every hop sender-constrained.** Transaction tokens are explicitly not replay resistant, and most product flows issue bearer tokens. Tessera binds every authorization-code token today; binding every exchanged token to the presenting hop's DPoP or mTLS key would make a stolen hop token useless elsewhere.
3. **Attenuation enforced and pinned by tests.** Scope and audience only shrink, expiry never extends, depth is capped, and each rule gets a threat-model row with a test that fails on regression, the same discipline as the existing seventeen rows.
4. **Keyless agents.** SPIFFE and cloud workload identity as first-class client authentication, so an agent never holds a stored secret.
5. **A clean MCP authorization server.** RFC 8707 at `/authorize`, Client ID Metadata Documents with the SSRF controls, the RFC 9207 metadata flag, and the stable client-credentials extension.

## Planned follow-ups and the standards each builds on

| Follow-up | Build on | Do not build on |
|---|---|---|
| Dynamic client registration for agents | Client ID Metadata Document (-02) first, as MCP prefers; RFC 7591 only as *protected* registration with an initial access token or software statement; SPIFFE client authentication for workload agents | Open RFC 7591 registration; RFC 7592 (experimental) |
| Agent delegation and token exchange (design) | RFC 8693 (`act`, `may_act`, `actor_token`); the actor-profile draft (-01) as design input; RFC 9449 and RFC 8705 for per-hop binding; RFC 8707 for audience; RFC 9396 for per-task consent; OIDF threat classification for threats | Transaction tokens for cross-boundary delegation (they are trust-domain internal and unbound) |
| The token exchange grant | RFC 8693, RFC 8707, RFC 9449, RFC 8705, RFC 9068, RFC 7009; identity chaining (-17) and ID-JAG (-04) as the next step | Impersonation semantics |
| Agent identity and attestation | SPIFFE client authentication (-02); the existing RFC 7523 trusted-issuer path; AIMS (-00) as the reference map; attestation-based client authentication (-12) when stable | Static API keys; vendor-specific agent identity models |
| MCP authorization support | MCP authorization 2026-07-28; RFC 9728 (resource side); RFC 8707 at `/authorize`; RFC 9207 metadata flag; Client ID Metadata Document; MCP client-credentials extension; ID-JAG for the enterprise-managed extension | Dynamic registration as the default path (deprecated by MCP) |
